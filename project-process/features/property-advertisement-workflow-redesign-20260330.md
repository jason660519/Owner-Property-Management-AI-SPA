# 物件廣告生成流程重規劃 Spec

日期：2026-03-30

適用頁面：superadmin/properties/[id]/edit?tab=advertisement_creators

## 背景

目前廣告生成功能以平台與風格 variant 為主軸，使用者需要先理解平台差異、樣式列、各列操作按鈕與下方 panel，才知道自己能不能產出想要的廣告。這與使用者真正的目標不一致。

使用者真正的任務是：

1. 決定這篇物件廣告要呈現哪些內容。
2. 選一種呈現風格。
3. 生成一份可預覽、可微調的廣告草稿。
4. 再決定要輸出到哪裡。

因此，本次重規劃改為內容導向，不再以平台導向流程作為主入口。

## 產品目標

1. 讓使用者在 30 秒內理解自己目前能生成哪些內容。
2. 把一次生成行為收斂為一個主要 CTA，避免表格式多入口。
3. 將「生成內容」與「輸出平台」拆開，降低格式與部署心智負擔。
4. 讓資料缺漏可被即時辨識，並能導回對應維護區塊。
5. 保留既有多平台能力，但將其移到生成後流程。

## 非目標

1. 本次不處理 Vercel 或 GitHub Pages 自動部署。
2. 本次不重新設計 HTML 模板引擎或 AI Prompt 架構。
3. 本次不新增新的 AI 風格模型，只重整流程與資訊架構。

## 核心設計原則

1. 先選內容，再選風格，最後才選輸出方式。
2. 內容可不可選，依據原始資料是否存在，不依據過去是否生成成功。
3. 一次只生成一份 canonical draft，其他平台視為輸出格式。
4. 任何 disabled 狀態都必須附原因與補資料入口。
5. 主要畫面以卡片與預覽為主，不再以表格列操作作為主體。

## 新流程總覽

### Step 0：資料完整度摘要

頁面進入後先顯示：

1. 可用內容數量，例如 5/8。
2. 缺少的關鍵資料，例如格局圖、權狀連結、地圖座標。
3. 快捷修正入口，例如前往照片、文件、地址與定位分頁。

目的：先讓使用者知道現在可以做出什麼，不必試點後才發現不能用。

### Step 1：選擇內容區塊

使用多選卡片或 checklist，讓使用者勾選本次廣告要包含的內容。

內容選項建議如下：

1. 物件基本資料
2. 物件介紹
3. 謄本連結
4. 建物與土地面積明細表
5. 權狀連結
6. Google 地圖定位
7. 物件照片
8. 物件格局圖

每個選項要有三種狀態：

1. available：可直接勾選
2. recommended：可勾選且建議勾選
3. unavailable：不可勾選，附缺漏原因與補齊入口

判斷依據：

1. 物件基本資料：永遠可選
2. 物件介紹：description 或 AI 文案存在
3. 謄本連結：對應文件存在且有可公開 URL
4. 面積明細表：已有結構化欄位或 OCR 解析結果
5. 權狀連結：對應文件存在且有可公開 URL
6. Google 地圖定位：latitude 與 longitude 存在
7. 物件照片：至少一張有效照片
8. 格局圖：floor plan 文件或圖像存在

預設值：

1. 物件基本資料：預設勾選
2. 物件照片：預設勾選
3. 物件介紹：若有資料則預設勾選

### Step 2：選擇頁面風格

使用單選卡片，不使用表格。

分為兩類模式：

1. 系統模板
2. 參考網址

#### 模式 A：系統模板

提供既有 4 個 style preset：

1. 豪宅暗色調
2. 清爽明亮
3. 商務簡潔
4. 溫馨日系

每個卡片要有：

1. 縮圖
2. 一句風格描述
3. 適合的物件類型提示

#### 模式 B：參考網址

使用者貼上外部廣告頁面 URL，系統嘗試抽取視覺語言。

規則：

1. 參考網址與系統模板不能同時生效。
2. 選擇參考網址後，系統模板僅作為 fallback，不作為主顯示狀態。
3. 若參考網址抓取失敗，需在生成前或生成後提示已退回系統模板。

### Step 3：生成廣告草稿

頁面僅保留一個主要 CTA：生成廣告草稿。

按下後執行：

1. 依已勾選內容組裝資料 payload
2. 依選擇的風格模式生成 canonical draft
3. 儲存草稿版本與內容配置
4. 導向下方預覽與編輯區

禁止行為：

1. 不再出現每列一個重新生成按鈕作為主路徑
2. 不要求使用者先選平台才可生成

### Step 4：預覽與微調

生成完成後顯示兩欄主區：

1. 左側：頁面預覽
2. 右側：可編輯設定

可編輯項目建議包含：

1. 廣告標題
2. 導語摘要
3. 聯絡 CTA 文案
4. 是否顯示各內容區塊
5. 區塊排序

若有重新生成需求，應從此區觸發，而非回到表格列操作。

### Step 5：輸出方式

將原本的發布平台改名為輸出方式，放在預覽與微調之後。

首版建議支援：

1. 本站頁面：建立或更新 Supabase/本站公開頁
2. Google Blogger：輸出 Blogger 可用格式並發布或手動貼上
3. 下載 HTML：下載獨立靜態頁，供使用者自行部署

未來可擴充：

1. Vercel 一鍵部署
2. GitHub Pages 一鍵部署
3. Facebook 粉絲頁摘要貼文輸出

## 資料模型建議

現有實作以 stylePreset、targetPlatform、referenceUrl identity 管理 variant。產品層建議再往前抽象一層：

1. canonical draft：內容與區塊配置的主版本
2. render variant：不同風格或平台的輸出結果

建議關係：

1. 一個 property 可有多個 canonical draft
2. 一個 canonical draft 可衍生多個 render variant
3. platform-specific post 僅記錄輸出結果，不作為唯一內容來源

這樣可避免目前「換平台等於換一份內容」的產品認知混亂。

## 主要 UX 問題與修正

### 問題 1：使用者先看到平台，不先看到內容

修正：平台下放到輸出階段。

### 問題 2：使用者無法快速知道哪些內容目前可用

修正：增加資料完整度摘要與 disabled reason。

### 問題 3：同一畫面有表格、各列按鈕與下方 panel，多入口造成猶豫

修正：整合成單一路徑 wizard + preview flow。

### 問題 4：參考網址與風格 preset 同時存在時語意不清

修正：改成二選一模式，並在 UI 直接反映 fallback 規則。

## 驗收標準

1. 使用者首次進入頁面即可看到可用內容總覽與缺漏資料。
2. 內容區塊的可選狀態完全由原始資料可用性決定。
3. 主流程中只保留一個「生成廣告草稿」主要 CTA。
4. 預覽與微調區取代原本表格列操作作為主工作區。
5. 平台選擇改為生成後的輸出方式選擇。
6. 參考網址與系統模板在 UI 上為互斥模式。

## 後續拆工建議

1. Phase 1：重構資訊架構與主畫面版型，不先動後端 AI 生成邏輯。
2. Phase 2：新增內容可用性聚合器，集中判斷 8 個內容區塊狀態。
3. Phase 3：建立 canonical draft 與 render variant 的產品層模型。
4. Phase 4：補生成後輸出流程與端到端測試。
