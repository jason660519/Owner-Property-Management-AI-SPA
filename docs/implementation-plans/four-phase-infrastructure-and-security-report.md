## 2. 四期軟硬體配置與 ROI 建議

原則：**Phase 1 全部架在家裡；Phase 2 起可視成長與維運負擔再導入雲端**。自建硬體需做好對外連線、備份與單點風險控管。

### 2.1 初期（約 100 房東客戶）— 全部架在家裡

**目標**：驗證產品、穩定訂閱，成本極小化，**整段服務（後端 + 前端 + 大檔）皆在家中環境運行**。

| 項目                 | 建議配置                                                                                                                                 | ROI 說明                                                                 |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **後端**             | **家裡自建**：Self-hosted Supabase（Docker）或 PostgreSQL + PostgREST/GoTrue/Storage 等效組合，跑在 **AMD PC** 或 **NAS**（若 NAS 可跑 Docker）。 | 無月租、資料全在自己家，適合初期驗證與成本敏感階段。                    |
| **前端**             | **家裡自建**：同一台 AMD PC（或 NAS）跑 Next.js（apps/web + apps/superadmin），經反向代理對外提供。                                     | 與後端同網段，延遲低；無 Vercel 月費。                                  |
| **大檔案（Storage）**| 同上，使用 Self-hosted Supabase Storage 或自建 S3 相容儲存（MinIO 等），與 DB 同機或同區網。                                             | 照片/權狀 PDF 不經雲端，頻寬與儲存成本為零（僅家裡電費與硬體）。        |
| **家裡硬體分工**     | **Mac Mini**：日常開發與維運。**AMD PC**：生產環境（Supabase + Next.js）。**NAS**：定期備份 DB、Storage 重要資料與設定（腳本 + cron）。   | 開發與生產分離；NAS 備份降低單點風險。                                  |
| **預估月成本**       | **0 USD**（老電腦 + 太陽能，主機與電費皆 0；浮動 IP 用 **Cloudflare Tunnel** 對外，無需固定 IP/DDNS）                                  | 以訂閱收入覆蓋容易，ROI 高；惟需接受「家裡即單點」的可用性 trade-off。  |

**結論**：Phase 1 **全部在家裡**，後端 + 前端 + 儲存一體；家裡設備需擔負對外連線、穩定性與備份責任。

#### 2.1.1 Phase 1 全家裡架設的建議與注意事項

| 面向           | 建議作法                                                                                                                                 |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **對外連線（浮動 IP）** | **推薦：Cloudflare Tunnel**。家裡主機跑 `cloudflared`，**出站**連到 Cloudflare，不需固定 IP、不需在路由器開 port、不需 DDNS。Cloudflare 提供穩定網址（自訂網域或 `xxx.trycloudflare.com`），HTTPS 由 Cloudflare 處理。見 [§2.1.2](#2112-浮動-ip--cloudflare-tunnel)。 |
| **HTTPS**      | 使用 Cloudflare Tunnel 時由 **Cloudflare 提供 HTTPS**（無需本機 Let's Encrypt）。**終止**指「TLS 終止」：瀏覽器與 Cloudflare 之間是加密連線，加解密與憑證都由 Cloudflare 負責；Cloudflare 再轉發到你家本機（可走 HTTP），本機不用裝憑證。若改採 port 轉發 + 自管網域，則用 Let's Encrypt（Caddy/certbot）。 |
| **防火牆**     | Tunnel 方案：**路由器無需開任何 port**，更安全。本機僅跑 cloudflared 出站；PostgreSQL、Supabase Studio 不對外，僅區網或 VPN。                        |
| **單點風險**   | 家裡斷電、斷網或硬體故障即服務中斷；建議：**UPS**、定期備份到 NAS，並可選將 **NAS 或雲端冷備一份**（如每週 rclone 到雲端 bucket）以便異地還原。 |
| **效能與容量** | AMD PC（16C/32T、64GB、4TB SSD）足夠約 100 房東；若流量上來可先優化 DB 與靜態檔快取，必要時再考慮遷部分服務上雲。                         |
| **開發與生產** | 開發可在 Mac Mini 跑同一 codebase 指到「家裡生產 Supabase」或另建一本地/雲端開發用 DB，避免直接改生產資料。                              |

#### 2.1.2 浮動 IP → Cloudflare Tunnel（推薦）

家中為 **浮動 IP**（例如 TPG 等 ISP）時，不必申請固定 IP 或架 DDNS，建議直接用 **Cloudflare Tunnel**（舊名 Argo Tunnel）：

| 項目 | 說明 |
|------|------|
| **原理** | 家裡主機安裝 **cloudflared**，主動**出站**連到 Cloudflare；流量經 Tunnel 進你家，**不需**在路由器開 80/443、不需公網 IP 固定。 |
| **優點** | 浮動 IP 無影響；路由器零 port 開放，更安全；Cloudflare 免費提供 HTTPS 與穩定網址；免費額度足夠 Phase 1。 |
| **網址** | 可先用快速網址 `xxx.trycloudflare.com`（每次重啟 tunnel 可能變）；或把自有網域 DNS 指到 Cloudflare 後，用 `yourdomain.com` 長期穩定。 |
| **本機架構** | 本機：Nginx/Caddy 或 Next.js 直接 listen 127.0.0.1:3000 / :3001；cloudflared 設定 `ingress` 把 `https://yourdomain.com` 轉到 `http://localhost:3000`（及 API 埠如 54321 若需對外）。 |

**簡要步驟**（依 [Cloudflare Tunnel 文件](https://developers.cloudflare.com/cloudflare-one/connections/connect-apps/) 為準）：

1. 註冊 [Cloudflare](https://dash.cloudflare.com/)（免費），若有自有網域可加入並將 NS 指到 Cloudflare。
2. 在生產主機（老電腦）安裝 **cloudflared**（[下載](https://developers.cloudflare.com/cloudflare-one/connections/connect-apps/install-and-setup/installation/) / `brew install cloudflared` 等）。
3. 執行 `cloudflared tunnel login`，用瀏覽器登入 Cloudflare 授權，取得憑證。
4. 建立 tunnel：`cloudflared tunnel create owner-pm`，再以 **config.yml** 設定 ingress（例：`https://yourdomain.com` → `http://127.0.0.1:3000`）。
5. 以 `cloudflared tunnel run owner-pm` 常駐運行（可搭配 systemd / launchd 開機自啟）。

**Cloudflare Tunnel 費用**（依官方與 FAQ，供 Phase 1 參考）：

| 項目 | 免費方案 | 說明 |
|------|----------|------|
| **Named Tunnel（自訂 tunnel）** | **0 USD/月** | 不需付費即可建立並長期使用；無需訂閱 Argo。 |
| **Tunnel 數量** | 每帳號最多 1,000 個 tunnel | Phase 1 僅需 1 個，足夠。 |
| **Routes（ hostname 路由）** | 每帳號最多 1,000 條 | 單一網域/子網域僅佔少數條，足夠。 |
| **同時連線數** | 無上限 | 免費方案不限制透過 tunnel 的並發用戶數。 |
| **Quick Tunnel（trycloudflare.com）** | 0 USD | 限 200 並發請求、無 SSE、網址重啟會變；僅適合測試，正式建議用 Named Tunnel + 自訂網域。 |
| **選購加價** | Argo Smart Routing 約 5 USD/月、Load Balancing 約 5 USD/月、Zero Trust Access 約 3 USD/月起 | Phase 1 可不買，維持 **0 USD**。 |

結論：Phase 1 使用 **Named Tunnel + 自訂網域（或免費網域）**，**Cloudflare 端月費為 0 USD**。

如此 **TPG 浮動 IP 無需任何設定**，對外一律經 Cloudflare，穩定又免 port 開放。

## 3. 大檔案儲存策略：雲端 vs 客戶端

### 3.1 您的情境整理

- **大檔**：物件照片、影片、權狀 PDF。
- **小檔**：房屋資訊、客戶資料（多為 JSON 等）。

### 3.2 「大檔案放客戶端」的兩種解讀

- **解讀 A：放在「房東的瀏覽器/本機」（例如 IndexedDB、本地檔案）**

  - 優點：省雲端儲存與頻寬。
  - 缺點：換裝置就看不到、無法在後台/租客端共用、備份與還原複雜、多裝置體驗差。
  - **結論**：不建議作為主要或唯一儲存，ROI 低且產品體驗差。
- **解讀 B：放在「每個房東的雲端空間」（即 Supabase Storage 依 tenant 隔離）**

  - 這就是目前 Supabase Storage + RLS 的用法：每個房東只存取自己的 bucket/路徑。
  - **結論**：維持即可，本報告建議在此基礎上優化（CDN、壓縮、多尺寸）。

- **解讀 C：放在「房東自己的 Google Drive」**

  - **優點**：我們不負擔儲存與頻寬成本；房東覺得「照片在我自己的雲端」、資料主權感高；Phase 1 零儲存成本可考慮。
  - **缺點**：房東須**綁定 Google 帳號**（OAuth），不用 Google 的房東無法用；要在 App 裡**顯示照片**必須透過 Google Drive API 讀取再轉發（我們仍會吃頻寬）或嵌 Drive 連結（權限、連結失效、版面難控制）；房東若刪檔、移檔、撤銷授權，App 內照片會斷線；多租戶時每個房東不同 Drive，維運與除錯較複雜。
  - **結論**：**可作為「備份／匯出到我的 Drive」的選配**；不建議作為**主要**照片儲存，否則顯示、權限、穩定性與體驗都難控。若堅持以 Drive 為主儲存，需接受：每房東 OAuth、後端 proxy 或 Google 直連的取捨、以及「房東動 Drive 我們就受影響」。

### 3.3 建議：大檔案仍以「雲端 Storage + CDN」為主

| 做法                            | 說明                                                                        |
| ------------------------------- | --------------------------------------------------------------------------- |
| **維持 Supabase Storage** | 依房東/tenant 隔離，權限與現有 Auth/RLS 一致，維運簡單。                    |
| **加上 CDN**              | 照片/影片/PDF 用 CDN 快取，減少重複下載、降低延遲與 egress 成本。           |
| **可選優化**              | 上傳時產生縮圖與多尺寸；列表/預覽只取縮圖，詳情再取原圖，進一步省頻寬。     |
| **不建議**                | 把大檔「只」放在房東本機/瀏覽器，作為唯一真相來源（同步與多端體驗問題大）。 |
| **房東 Google Drive**    | 僅建議作**選配**：例如「匯出／備份到我的 Drive」。不建議作主要儲存：需每房東 OAuth、顯示需 API 或嵌連結、房東刪檔/撤權即斷線，維運與體驗難控。見 [§3.2 解讀 C](#32-大檔案放客戶端的兩種解讀)。 |

若未來頻寬與儲存成本成為明顯瓶頸，可再評估：
**「原檔」存廉價物件儲存（如 R2）+ CDN，「中繼/縮圖」仍可放 Supabase**，而不必改為「客戶端本機儲存」。

## 4. 防盜版與存取控制建議

### 4.1 Auth 能控制什麼、不能控制什麼

- **Auth 能做的**：
  - 控制「誰能登入」與「誰能存取哪些資料」（透過 Supabase Auth + RLS）。
  - 未登入或無權限的用戶無法讀寫您的 DB 與 Storage，**等於無法合法使用您的後端服務**。
- **Auth 不能做的**：
  - 無法防止有人「複製前端程式碼」、反編譯、或做出一份看起來類似的 UI。
  - 無法防止離線盜版或 100% 防止有心人繞過前端檢查（前端程式碼本就可被檢視）。

因此：**Auth 是「存取控制」與「訂閱制收費」的基礎，不是「防拷前端」的工具。**

### 4.2 建議的防盜版與保護策略

| 層級                              | 做法                                                                                                | 說明                                           |
| --------------------------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| **1. 後端強制驗證（必做）** | 所有 API、DB、Storage 皆需**Auth + RLS**；不信任前端傳來的「身份」，一律以 JWT/session 為準。 | 沒帳號就無法用您的服務，複製前端也拿不到資料。 |
| **2. 訂閱與授權**           | 依訂閱狀態（例如 Stripe/金流）決定能否使用進階功能或存取更多資料；狀態存在後端，前端僅顯示。        | 盜版者無法取得有效訂閱即無法享受完整服務。     |
| **3. 前端基本防護（可選）** | 環境變數不暴露關鍵 key；可做程式碼混淆（例如 Terser）、不放置敏感邏輯。                             | 提高抄襲門檻，無法從根本防止。                 |
| **4. 合約與法律**           | 使用者條款、訂閱合約中載明禁止未授權重製、轉售、逆向。                                              | 發生糾紛時有依據，具嚇阻效果。                 |
| **不建議**                  | 投入大量資源做「無法被破解」的前端保護。                                                            | 前端本質上可被檢視，ROI 低。                   |

**總結**：

- **用 Auth 控制「誰能存取後端」**：能有效防止未付費或未授權者使用您的系統。
- **防「被 copy 盜版」**：靠「後端唯一真相 + 訂閱綁定 + 合約」，而非單靠前端保護。

---

## 5. 總結與行動建議

### 5.1 四期軟硬體與 ROI

- **初期（100 戶）**：**全部架在家裡** — AMD PC 跑 Self-hosted Supabase + Next.js，Mac Mini 開發，NAS 備份；對外經 DDNS/固定 IP + 反向代理 + HTTPS。
- **中期（500 戶）**：可從家裡遷上雲（Supabase Pro + Vercel）或維持家裡擴容；NAS 備份強化，可選 CDN。
- **爆發期（5,000 戶）**：雲端為主；Storage 前加 CDN、必要時大檔遷 R2/S3；家裡設備做備份與 CI/Staging。
- **成熟期（50,000 戶）**：雲端與 CDN 為主，家裡設備僅備份與開發；依規模評估 Enterprise 或自建。

整體原則：**Phase 1 全家裡以壓低成本與驗證產品；Phase 2 起視成長與可用性需求再導入雲端，家裡硬體轉為備份與開發。**

### 5.2 大檔案

- **建議**：大檔案（照片、影片、權狀 PDF）維持 **雲端 Storage（Supabase 或未來 R2/S3）+ CDN**。
- **不建議**：把大檔「只」放客戶端（房東本機/瀏覽器）當唯一儲存，因同步、多裝置與備份問題會拉低體驗與 ROI。

### 5.3 防盜版與存取控制

- **Auth 能控制**：誰能登入、誰能存取哪些資料（必做，且所有 API/Storage 都應強制驗證）。
- **Auth 不能防止**：前端程式碼被複製或模仿。
- **建議**：後端強制 Auth + RLS、訂閱綁定、合約條款，加上前端基本防護即可；不建議重金投入「完全防拷」。

## 6. 初期／中期執行檢查清單

以下為「初期（約 100 戶）」與「中期（約 500 戶）」可依序勾選的執行清單，方便逐項落實。

### 6.1 初期（約 100 房東客戶）檢查清單 — 全部架在家裡

#### 家裡生產環境（AMD PC 或可跑 Docker 的 NAS）

- [ ] **Self-hosted Supabase**：已用 Docker 跑起 PostgreSQL + Auth（GoTrue）+ Storage + PostgREST（或官方 [supabase/supabase](https://github.com/supabase/supabase) 自建腳本）；僅 Listen 127.0.0.1 或區網，不對外暴露 5432。
- [ ] **Next.js**：apps/web、apps/superadmin 已建置並跑在同一台或同區網，環境變數指到家裡 Supabase 的 URL（例如 `http://localhost:54321` 或內網 IP）。
- [ ] **反向代理**：Nginx 或 Caddy 已安裝，對外 80/443 轉到 Next.js；**未**對外開放 DB、Supabase Studio 等埠。
- [ ] **HTTPS**：已用 Let's Encrypt（Caddy 自動或 certbot）取得憑證，對外僅提供 HTTPS。
- [ ] **對外連線（浮動 IP）**：已用 **Cloudflare Tunnel**（cloudflared）對外，無需固定 IP/DDNS、無需路由器開 port；網域或 `xxx.trycloudflare.com` 可從外網連到服務（見 [§2.1.2](#2112-浮動-ip--cloudflare-tunnel推薦)）。

#### Auth、Storage 與資安

- [ ] **Auth**：登入/註冊流程正常；RLS 已套用在主要表（例如 `properties`、`profiles`）。
- [ ] **Storage**：照片/檔案上傳用的 bucket 已建立，RLS 政策僅允許已登入且具權限的用戶存取。
- [ ] 所有 API / DB / Storage 存取皆需 Auth，無「僅靠前端隱藏」的敏感操作。
- [ ] 訂閱/付費邏輯（若已上線）：訂閱狀態存在後端，前端僅顯示；未訂閱無法使用付費功能。

#### 家裡硬體與備份

- [ ] **Mac Mini**：開發環境可正常跑 `./start.sh` 或各 app，可連家裡生產 DB（僅區網/VPN）或另建開發用 DB；必要時可遠端連線處理。
- [ ] **NAS 備份**：已排程（cron 或 NAS 內建）定期備份：
  - [ ] 家裡 PostgreSQL 匯出（pg_dump）。
  - [ ] Storage 重要檔案（或整個 bucket）複製到 NAS（rclone / rsync）。
  - [ ] 重要設定與腳本（env 範本、Nginx/Caddy 設定、部署腳本）複製到 NAS。
- [ ] **還原演練**：至少做過一次「從 NAS 備份還原 DB + 設定」的練習。
- [ ] **可選**：UPS 防斷電；異地冷備（例如每週將備份上傳到雲端 bucket 一次）。

## 7. 開發階段改用雲端 Supabase 建議

**若 Phase 1 已採「全部架在家裡」**：開發環境可選擇 **(A) 指到家裡同一台 Self-hosted Supabase**（另建 dev schema 或 dev 專案避免污染生產），或 **(B) 仍用雲端 Supabase Free 專案做開發**，生產維持家裡。兩者皆可，視你偏好「完全離線可開發」或「開發/生產環境一致（皆家裡）」而定。

以下為「開發階段是否改用雲端 Supabase」的建議（適用於你考慮把開發從本地 Docker 改為雲端時）。

### 7.1 建議：可以，且多數情境下更省事

| 做法 | 說明 |
|------|------|
| **建議** | 開發階段就使用 **雲端 Supabase Free 專案** 作為唯一後端，本機不再跑 `supabase start`（Docker）。 |
| **理由** | Free 額度足夠一人開發；環境與日後正式環境一致，減少「本機正常、上線異常」；不需開 Docker、不需維護本地 DB，開機即可開發。 |

### 7.2 實作要點

1. **專案分離**  
   - 在 [Supabase Dashboard](https://supabase.com/dashboard) 建立一個 **僅供開發用** 的專案（例如命名 `owner-pm-dev`）。  
   - 日後正式上線再建一個 **生產專案**（例如 `owner-pm-prod`）。  
   - 開發與生產的 `NEXT_PUBLIC_SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY` 等不要混用。

2. **本機設定**  
   - 在 `apps/web/.env.local` 與 `apps/superadmin/.env.local` 中設定雲端專案的 URL 與 keys（從 Supabase 專案 Settings → API 取得）。  
   - **不要**把雲端 key 提交到版控；`.env.local` 已在 `.gitignore` 即可。

3. **Migration 與 Schema**  
   - 現有 `supabase/migrations/` 的 SQL，改為對 **雲端開發專案** 執行：  
     - 在專案根目錄執行 `supabase link --project-ref <開發專案 ref>` 連結到該雲端專案，  
     - 之後用 `supabase db push` 或依專案既有流程推送 migration。  
   - 或先在 Dashboard 手動建表、之後再用 migration 補齊版本管理亦可。

4. **啟動腳本**  
   - 若採用「開發一律用雲端」，`start.sh` 可 **不再** 呼叫 `supabase start` 與 `ensure_web_env_supabase`（不再從本地 Supabase 寫入 key）。  
   - 改為：依賴各 app 的 `.env.local` 已手動或一次性設定好雲端 URL/keys；`./start.sh` 只啟動 Next.js、OCR 等服務。  
   - 若希望保留「可選本地」：可加環境變數（例如 `USE_CLOUD_SUPABASE=1`），當設為 1 時跳過 `supabase start` 與 key 寫入，仍從 `.env.local` 讀取雲端連線。

### 7.3 優缺點簡表

| 面向 | 開發用雲端 Supabase | 開發用本地 Supabase |
|------|---------------------|----------------------|
| 需 Docker / Supabase CLI 本機跑 DB | 否 | 是 |
| 與正式環境一致度 | 高 | 較低（本地與雲端可能有差異） |
| 離線能否開發 | 否（需網路） | 是 |
| Free 額度 | 足夠 1 人開發 | 無額度問題（本機） |
| 遷移／還原演練 | 可直接用同一雲端專案或複製專案 | 需本機備份還原 |

### 7.4 注意事項

- **不要用生產專案做開發**：開發用專案與生產專案分開，避免測試資料或錯誤 migration 影響真實客戶。
- **Auth / Storage**：雲端專案會啟用真實的 Auth 與 Storage；測試帳號、測試檔案請只在開發專案使用，並注意不要誤貼生產 key 到前端。
- **成本**：Free 方案有額度上限（DB 大小、API 請求等），一人開發通常不會超過；若將來要多人共用一个開發專案，再考慮升級或每人一專案。

總結：**開發階段就把 Supabase 移到雲端（單一開發用 Free 專案）是合理且推薦的**；本機僅需設定好 `.env.local` 並可選簡化 `start.sh`，不再依賴本地 Docker Supabase。
